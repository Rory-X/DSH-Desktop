# DSH 大量 API Failed to fetch 排查与修复

核查日期：2026-09-18，Asia/Shanghai。

## 结论

**状态：修复了一个确定的故障来源，但尚未根治用户报告的间歇性复发。**

2026-09-18 17:33 左右，用户报告“新会话”再次无响应，并说明其它问题复现。
随后用户确认当前恢复正常，但发送反馈前确实发生过故障。
因此，下文的短时间验证不能证明长期使用已经稳定；此前“核心 API 已恢复正常”
的结论只适用于当时的观察窗口，不应表述为所有问题均已根治。

已确认 `DSH-Plugs/plugins/dsh-synapse` 的会话同步会触发一条大面积网络失败链路。
当时携带桌面 Cookie 的直接 RPC 正常，未发现模型 API Key 失效或服务整体不可用。

现场环境为 DSH `0.1.6-alpha.2`，桌面运行时 Node `26.8.2`。
用户页面出现 `session/prompt`、`terminal/list`、`workspaceFiles/read`
的 `Failed to fetch`。携带桌面 Cookie 直接调用真实 RPC 时，
`session/list` 和 `terminal/list` 均正常成功。

## 故障链

1. 会话地图客户端在列表、工作区、当前会话和状态通知时上传整个会话快照。
   现场有 573 个会话，单次同步请求达到 133,705 字节。
2. `/synapse/api/sessions/sync` 共用的 JSON 读取器只允许 32 KiB。
   超限时直接从 `for await (const chunk of req)` 抛错，提前终止
   `IncomingMessage` 的异步迭代。
3. 拒绝响应仍声明 HTTP keep-alive，但连接已经不能继续正常处理请求。
   Chromium 复用它请求其他 API 后等待约 6 秒，最终收到
   `ERR_CONNECTION_RESET`。网络日志中确认影响了命令、模型和插件接口。
4. 微任务级合并不足以限制持续的状态通知；每次通知又提交完整快照，
   持续产生超限请求和排队，最终在页面表现为多种 API 同时失败。

隔离 HTTP 测试复现了相同现象：超限同步返回后，同一连接上的下一条正常
请求无法完成。修复前测试在 1 秒超时；修复后可持续复用同一连接。

## 修复位置

修复位于同机插件仓库，不需要重打包桌面应用：

- `../DSH-Plugs/plugins/dsh-synapse/index.js`：
  请求超过上限后停止保留内容，但继续读完请求体，再返回原有的 400
  校验错误。保留 32 KiB 上限，不提前破坏共享连接。
- `../DSH-Plugs/plugins/dsh-synapse/client.js`：
  按 UTF-8 字节数分批，每批最多 24 KiB；只同步持久元数据变化；
  同时仅允许一个同步请求；成功响应后更新已同步状态；
  失败时保留未确认的更新和删除，退避重试；卸载时取消定时器和请求。
- 新增 `test/http-body.test.js`、`test/session-sync.test.js`，
  并更新 `test/turn-preview.test.js` 的生命周期依赖。

保留了插件仓库和桌面仓库原有的未提交改动。没有升级 DSH，
没有改动官方安装包源码，也没有关闭会话地图功能。
